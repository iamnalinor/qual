# Работа над Qual

Основная ветка — `main`. Для сборки нужен Go 1.27.4 и Git. Скрипт подготовки окружения рассчитан на Linux x86_64; ему также нужны Bash, curl, tar, Python 3, Node.js и утилиты SHA-256.

## Подготовка и запуск

```sh
./scripts/bootstrap
export PATH="$PWD/.tools/bin:$PATH"
just build
./bin/qual --help
```

Bootstrap скачивает закреплённые версии инструментов в `.tools/bin` и зависимости Go. Для этого нужен интернет. Ключи моделей для сборки и обычных тестов не нужны.

## Проверки перед отправкой изменений

```sh
just fmt
just lint
just test
```

`just fmt` форматирует Go-код. `just lint` проверяет форматирование, ошибки Go, shell-скрипты и GitHub workflows. `just test` запускает обычные тесты с детектором гонок. Команда `just check` объединяет линтеры, сборку и тесты.

Для проверки команд приложения используется `just test-e2e`: он запускает настоящий бинарный файл с временными Git-репозиториями и локальными HTTP-серверами. Эти тесты не обращаются к моделям. Если меняете поведение на границе с Git, файловой системой, процессами или HTTP, предпочтительнее проверить эту границу целиком. Юнит-тесты полезны для нетривиальной логики, например расчёта бюджета.

`just test-llm` — отдельный набор с реальными моделями. Для него нужны явное включение, настроенный ограничитель общего бюджета и тестовые учётные данные. Обычные проверки не запускают его автоматически; инструкции находятся рядом с тестами в `tests/live/`.

## Проверка sandbox

Нужен Linux с разрешёнными пользовательскими и сетевыми namespace, а также bubblewrap, socat, ripgrep, which, Python 3 и Node.js не ниже 22.12.

```sh
npm ci --ignore-scripts --prefix sandbox
just test-sandbox
```

Если окружение не разрешает нужную изоляцию, проверка завершается ошибкой. Это не считается успешно пройденным тестом. GitHub CI подготавливает отдельный runner для этих проверок.

## Устройство кода

Модели данных и контракты находятся в `internal/domain` и `internal/port`. `internal/runtime` управляет выполнением ревью, а `internal/app` соединяет его с адаптерами и интерфейсом команд. Подробности и границы пакетов описаны в [архитектуре](docs/architecture.md).

При продолжении сессии нельзя менять её снимок, принятые настройки или накопленные расходы. Если неизвестно, успел ли инструмент изменить файлы до прерывания, повторять его автоматически нельзя.

Настройки проверяемого репозитория не могут выдавать учётные данные, менять адрес провайдера, повышать жёсткие лимиты расходов или расширять права MCP. При изменении конфигурации сохраняйте информацию о происхождении значений.

## Стиль и зависимости

Код, комментарии и имена пишем по-английски. Конфигурация golangci-lint проверяет в том числе обработку ошибок, границы пакетов и сложность функций. Для производственного кода установлены пределы: цикломатическая сложность 10, когнитивная 15, длина 80 строк и 40 операторов. Для длинных интеграционных сценариев есть отдельные исключения в общей конфигурации.

Сообщение об ошибке должно объяснять, какая операция не удалась, и сохранять исходную причину. Полезно добавить следующий шаг, если он известен. Обычный вывод предназначен для человека; `--json` сохраняет стабильный машинный формат.

`just vuln` проверяет Go-зависимости по публичной базе уязвимостей, `just vuln-sandbox` — зависимости npm. Обе команды требуют сети. Известное ограничение зависимостей sandbox описано [отдельно](docs/sandbox-dependencies.md); не скрывайте результат аудита несовместимым обновлением пакета.

## GitHub CI

Проверки выполняются для `main` и pull requests. CI запускает обычные и sandbox-тесты, а также собирает бинарные архивы для Linux/macOS на amd64/arm64. [Инструкция по скачиванию](docs/ci.md#download-ci-binaries) пригодится для ручной проверки конкретного коммита.

В описании изменения укажите, какое поведение исправлено и как оно проверено. Для изменений интерфейса покажите реальный сценарий работы в терминале, включая ошибку или отмену, если они затронуты.
